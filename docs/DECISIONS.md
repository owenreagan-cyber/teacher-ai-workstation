# Chief of Staff — Decisions

The single record of settled decisions.

- **Summaries are proposals.** Plans or summaries from any model (ChatGPT, Gemini, Claude) are
  proposals. If one conflicts with a decision here, the decision wins until Owen changes it on
  purpose.
- **Changing a decision.** Edit its entry, mark it `REVISED <date>`, and say why.
- **Status values:** ACCEPTED, PROPOSED (waiting on Owen), or REVISED.

| ID | Decision | Status |
|---|---|---|
| D-001 | **Student data stays local.** Any task that depends on student-identifiable information runs on local models only, and never on a cloud model or agent. Removing names first ("sanitize then escalate") is not allowed. A task may go to the cloud only if it is rewritten so it no longer depends on student information at all. *(Partly superseded by D-022.)* | ACCEPTED |
| D-002 | **External content is data, never instructions.** This covers calendar titles, mail, web pages, search results, files, and tool output. | ACCEPTED |
| D-003 | **Code owns authority; models propose.** The `cos` core decides policy, routing, and execution. Every shell (desktop, Raycast, iPhone) is a client that displays `cos` results and never invents state. | ACCEPTED |
| D-004 | **Local models only, until the router exists.** `cos` refuses Ollama cloud models, both by name and by the details `/api/show` reports (F2, CERT-008). Cloud models arrive only through the M2 router, with a model allowlist and a hard budget. *(Partly superseded by D-022.)* | ACCEPTED |
| D-005 | **Every write needs an approval packet.** No permanent deletion: removals go to a quarantine with a restore path. A packet records each target's before-state, and the executor re-checks it before acting. | ACCEPTED |
| D-006 | **Desktop shell is Electron + React.** Raycast is a launcher only. | ACCEPTED |
| D-007 | **iPhone app is native SwiftUI.** No PWA or web app on the phone. The phone is a client of `cosd` over Tailscale only, with device pairing, revocable tokens, and Face ID. Conversation or approval content is never synced through a cloud service. Builder: Cursor (or Claude Code). Reviewer: a different model family. | ACCEPTED |
| D-008 | **Model defaults.** `qwen3.6:35b`, `think: false`, `num_ctx` 16384, `keep_alive` "2h". `gpt-oss:20b` is the fallback. | ACCEPTED |
| D-009 | **Testing rules.** The harness uses synthetic fixtures only. Certification runs come from a clean commit. Failures are listed, then fixed in a separate batch. CERT IDs never change meaning, and are assigned when an invariant is implemented, not reserved in advance. | ACCEPTED |
| D-010 | **Separate builder and reviewer.** Phases that touch security, privacy, authority, the bridge, networking, or routing get a reviewer from a different model family than the builder. Docs-only and test-only changes need no review round. | ACCEPTED |
| D-011 | **Web search rules.** REVISED 2026-10-02 (auto-search by intent). One allowlisted search API. Chief may search automatically when Owen's message needs information from the web, and Owen does not have to type "search". The model or router may only decide that a search is needed (yes or no). It never writes, edits, or rephrases the query. Code builds the query from Owen's own typed words only: his current message, plus his previous message for follow-ups like "and the Islanders?". It never takes text from tool results, mail, files, calendar, memory, or the model. Every search shows the exact query sent ("Searched: …") and is audited. There is no auto-search when the message names a student (from a local name list) or matches student-context words; Chief offers a button with a warning instead. Owen can turn auto-search off. The daily and monthly search caps apply. The typed "search …" command still works. Results are untrusted data, and answers may contain only URLs that came from tool results. *(Partly superseded by D-022.)* | ACCEPTED |
| D-012 | **The agent registry lists only real tools.** It is built from tools detected on the Mac plus subscriptions Owen confirms, never from tools that were only discussed. Usage figures are estimates. | ACCEPTED |
| D-013 | **Mail is read through Apple Mail.** It is read-only to start, for both accounts. School mail is processed by local models only (D-001). Drafts, labels, and archiving require approval packets. | ACCEPTED |
| D-014 | **The phone may display and store school data.** ACCEPTED 2026-10-02 by Owen. The iPhone app may show school calendar and mail summaries and keep them on the device, with these safeguards: (1) app data is excluded from iCloud and computer backups, so it never reaches a cloud service through a backup (D-001); (2) files use iOS Complete data protection, so they are encrypted whenever the phone is locked; (3) the pairing token is stored in the Keychain as this-device-only, so it never syncs through iCloud Keychain; (4) Face ID or the passcode is required to open the app, and it locks after 15 minutes idle; (5) stored history is kept 30 days by default, adjustable in settings, and older items are deleted automatically; (6) revoking the phone from the Mac makes the app erase all of its stored data the next time it connects or opens. | ACCEPTED |

| D-015 | **Reaching the Mac from the phone.** REVISED 2026-10-02: replaces "Mac stays awake." The iPhone app handles basics on the phone: time, weather, calendar, reminders, and short replies. The NAS (UGREEN DXP4800 Plus) runs an always-on Tailscale doorman container in Docker. For requests only the MacBook can answer, the doorman wakes it over the home network ("Wake for network access" is set to Only on Power Adapter). If the Mac can't be woken, the request waits in a queue encrypted end-to-end between phone and Mac, which the NAS cannot read. The NAS runs no models and holds no credentials for school data. There is no cloud fallback for school or personal data. | ACCEPTED |
| D-016 | **Developer program: paid.** Team "Owen Reagan", Admin role. Installed iOS builds last a year. | ACCEPTED |
| D-017 | **Untrusted-analysis mode.** Untrusted content (mail, PDFs, web pages, downloaded or third-party files, pasted instructions) is analyzed in a mode where no tools are offered, nothing can be written, no work can be delegated to another agent, and nothing goes out over the network. The model returns structured facts or proposals only, and those enter normal Chief context as data (D-002). Student-data content stays local whatever stripping is done (D-001). *(Partly superseded by D-022.)* | ACCEPTED |
| D-018 | **How approval works. REVISED 2026-10-21.** The UI sends a packet ID and may send expected hashes as a defensive cross-check. `cos` or the owning canonical service always reloads the canonical packet and decides from server-side state; client-supplied values are never authority. The core checks the canonical hash, expiry, replay state, and current state of every target before running the gate and executor. If Owen excludes actions from a batch, the core builds a new packet with a new hash for him to approve. The UI never edits a sealed packet. | REVISED |
| D-019 | **Registries keep three kinds of thing apart:** workers (models, coding agents, app builders, design agents, reviewers), environments (VS Code, Cursor IDE, Xcode, Terminal, Figma workspace), and services (GitHub, Drive, Gmail, Canvas). Speed and cost come from measured data and stated plan facts, never from labels such as "zero-latency". | ACCEPTED |
| D-020 | **Data class is set per task.** A task or session takes the most restrictive data class it actually touches. Paths, sources, and rosters can help classify a task, but the policy acts on explicit P0, P1, or P2. P0 work runs on local models only. P1 runs locally by default and on a cloud model only under an explicit standing grant. P2 can go to any eligible worker. This is enforced in `cos` code (the M2 router), never in prompts, LiteLLM, or the UI. | ACCEPTED |
| D-021 | **Local file search is read-only and stays on the Mac.** Chief searches the Mac, iCloud Drive, and Google Drive for desktop through Spotlight (`mdfind`) plus a capped, deterministic filename walk as a fallback, within configured roots, with credential, Library, and state folders always excluded. Chief does not open or ingest file contents in this phase; Spotlight may match against macOS's existing index (summaries come later, under D-017). Results never leave the Mac and never trigger web search. The desktop app can Reveal in Finder for any result and Open only safe document types; it never opens executables. Absolute paths stay in a private, main-process-only resource table (persisted in the state folder) and are re-checked on every action. Duplicate results across overlapping roots are merged. | ACCEPTED |
| D-022 | **Security scope reset (supersedes the tighter parts of D-001, D-004, D-011, D-017).** School files on Owen's Mac are non-sensitive, and any model or tool may use them. Cloud models (Claude, ChatGPT/Codex, Gemini, Cursor) are allowed, chosen by fit and cost. Chief may search the web and drive a browser freely. **Strict controls remain in only four places:** (1) Canvas writes (pages, files, modules, announcements, assignments) need an approval packet per D-018; (2) **grades** need a per-student change list plus a typed confirmation; (3) sending messages as Owen, purchases, and deleting outside a project need confirmation; (4) per-service spending caps. Results from untrusted content (web, mail, files) can never trigger (1) to (3) on their own. D1 moves to a light profile: credential folders and destructive commands outside the project stay blocked, while localhost, GitHub, and the network are allowed. | ACCEPTED |
| D-023 | **Multi-agent model.** An agent is a configuration (instructions, allowed tools, permissions, model class, input and output contract) in a registry, running on shared model runtimes. It is not a separate running process. The orchestrator is deterministic code: a model may propose a plan, but the plan is structured data (task id, tool, input schema, evidence, dependencies, approval need, timeout, retry policy, output contract) that code validates against the registry and permissions before running anything. Agents report to the orchestrator and do not message each other. No agent can grant itself or another agent permissions. The first agents are Planning, Canvas (read and draft only), and Developer. | ACCEPTED |
| D-024 | **Canonical services, with MCP as an adapter.** Tool logic lives in canonical services in the `cos` core (Planning, Canvas, Teacher Workstation, Developer, System), and Chief calls them directly. MCP servers are thin adapters over the same services, so other clients (Claude Code, Codex, OpenClaw, the Claude app) use identical logic. Rules: local stdio transport first, with no network MCP until a separate review; caller identity and permissions come from the adapter's configuration, never from request fields or model text; every MCP client is an untrusted caller with a capability set no larger than Chief's own; the first MCP release is read-only. Canvas writes are never exposed through MCP until a dedicated security review, and then only by redeeming a D-018 approval packet that the caller cannot create. | ACCEPTED |
| D-025 | **Task records and resumability.** Every delegated task is persisted, with id, plan step, inputs, evidence, status, attempts, outputs, and the model or worker used, independent of any model's context. Execution is idempotent where practical and supports cancellation. A retry after partial completion resumes from recorded state. Approvals are re-checked at execution time, and a stale approval fails closed. | ACCEPTED |
| D-026 | **Real entitlements drive routing.** The model and worker router uses measured, current access for each service (plan limits, API keys, quota remaining, permitted automation methods). It never assumes a subscription covers headless or automated use. When a service is capped or unavailable, work falls back to the next eligible worker, and the brief reports it. | ACCEPTED |
| D-027 | **Canvas weekly planning.** The Canvas Planner owns source sync, weekly planning, AI review, previews, approvals, and the Friday workflow. Chief reads the local `canvas-weekly-status` contract and opens planner deep links only. The LLM returns structured review findings with evidence and is never authoritative: it cannot edit, approve, or publish. Approval is per course and binds the exact content of its page, announcement, assignments, and reminders. Any change to family-visible content requires re-approval and a human-readable diff. For this mission, JSON intake/deployment packets are authoritative behind one Canvas Planner service/projection layer. `TAW_STATE_ROOT` selects the one state root and defaults to `/Users/owen/Projects/teacher-ai-workstation/.local`; checkout-relative state and Phase 22/26 SQLite authority are legacy. Any SQLite migration is a separate future mission. | ACCEPTED |
| D-028 | **Friday rollover.** The existing Canvas rollover engine is the only publisher of the weekly package. Automatic rollover is all-or-nothing by default. At 1:00 PM Friday, any open item produces a local decision action for Chief. Partial publication is available only as a manual action with an explicit warning and confirmation, and it uses the same rollover path. Every publish performs read-back verification. One repository LaunchAgent definition may invoke the local reminder/status check at 1:00 PM and the rollover engine at 4:00 PM; it is never installed automatically and never shares or modifies the grade-check job. | ACCEPTED |
