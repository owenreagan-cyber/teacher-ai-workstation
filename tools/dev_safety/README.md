# D1 — developer safety for Claude Code sessions in this repo

D1 keeps a Claude Code agent working in this repo away from student data, credentials,
Claude Code's own configuration and transcripts, and destructive or outward-facing commands
(push, force, privilege escalation).

## What it protects

- **Student data:** `~/.teacher-ai-workstation` and the Chief of Staff state directory
  (`~/Library/Application Support/ChiefOfStaff`).
- **Credentials:** `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`.
- **Downloads:** `~/Downloads`.
- **Claude Code state:** `~/.claude.json`, `~/.claude/settings.json`,
  `~/.claude/settings.local.json`, and everything under `~/.claude/projects` (session
  transcripts and memory), for reads and writes.
- **The profile itself:** `<project>/.claude` and the installed hook directory
  `~/.claude/hooks/cos`.
- **Git:** push, config, clean, gc, update-ref, `reset --hard`, force flags, `-c alias.*`, and
  worktree add/remove/move/prune outside `$COS_FEATURE_WORKTREE`.
- **Inline code:** any shell run as a program (`bash x`, `sh -c`, `xargs sh -c`), `python -c`,
  `node -e/--eval/-p`, `perl -e/-E`, `ruby -e`, `php -r`, `osascript`, `deno eval`, `bun -e`,
  `lua -e`, `Rscript -e`, `awk` programs with `system(` or a pipe, and interpreters reading
  their program from stdin, also behind `env`, `xargs`, `nice`, `timeout`, `exec`, and
  `find -exec`. Running a file or module (`python3 -m unittest`, `python3 x.py`, `npm test`)
  stays allowed.
- **Destructive commands:** `rm -r` and `rmdir` outside the worktree or system temp,
  `find -delete`, `shred`, `dd if=/of=`, `mkfs`/`newfs`, `diskutil erase*/zero*/reformat/
  partition*`, `tmutil delete*`, `brew uninstall/autoremove/cleanup`, `docker rm/rmi/… prune`.
- **Process listings** that print full command lines (`ps aux`, `pgrep -fl`, and similar).
- **Privilege escalation:** `sudo`, `doas`, `su`.

Bash paths are resolved like the shell would: relative words and redirection targets against
the working directory (including any `cd` earlier in the same command), `~`, `$HOME`, and
symlinks. A glob or variable is judged by its literal prefix, and a recursive tool (`grep -r`,
`find`, `rg`, `tar`, `cp -r`, …) whose base contains a denied root is denied.

## The layers

1. **OS sandbox (the boundary).** Claude Code's built-in Bash sandbox, enforced by macOS
   Seatbelt on every Bash command *and every process it starts*. This is what contains
   `python3 x.py`, `npm test`, and `make`, which no command check can see into.
2. **Claude Code permission rules** (`permissions.deny`). They gate the file tools (Read, Edit,
   Write), which the sandbox does not cover, and add simple Bash prefix denials.
3. **The PreToolUse hook** `dev_guard.py` (the second layer), installed read-only to
   `~/.claude/hooks/cos/`. It parses each Bash command and file-tool payload and denies what the
   rules would miss (normalized git forms, symlinks, relative paths, inline interpreters,
   nested wrappers, MultiEdit `edits[].file_path`).

### What the sandbox enforces

Both settings files are generated by `render_settings.py`; edit that file (or
`student_data_roots.txt`), re-run it, and commit the output.

| File | Where it goes | Who puts it there |
|---|---|---|
| `settings.proposed.json` | `<repo>/.claude/settings.json` | Owen (`cp`); the agent cannot write `.claude/` |
| `sandbox-lock.json` | `~/.claude/hooks/cos/sandbox-lock.json`, read-only | `install_dev_guard.py` |

Start sessions with `claude --settings ~/.claude/hooks/cos/sandbox-lock.json`. With the lock:

- **Bash is always sandboxed.** `enabled`, `failIfUnavailable` (Claude Code refuses to start if
  the sandbox can't), and `allowUnsandboxedCommands: false` (the `dangerouslyDisableSandbox`
  retry is ignored). There are no `excludedCommands`.
- **Reads denied** to sandboxed commands: `~/.teacher-ai-workstation` and the other
  student-data roots, `~/Library/Application Support/ChiefOfStaff`, `~/Downloads`, `~/.ssh`,
  `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/.netrc`, `~/.docker`, `~/.kube`, `~/.npmrc`,
  `~/.pgpass`, `~/.config/op`, `~/.config/gcloud`, `~/.claude.json`,
  `~/.claude/settings.json`, `~/.claude/settings.local.json`, `~/.claude/projects`.
- **Writes** go only to the working directory, the per-user temp directory (`$TMPDIR`),
  `/tmp` and `/private/tmp`. Claude Code also allows writes to the main repo's shared `.git`
  directory when the working directory is a linked worktree (except its `hooks/` and
  `config`), and always denies writes to `.claude/` settings, hooks, skills, `.mcp.json`,
  `.git/hooks`, `.git/config`, shell startup files, and most of `~/.claude`.
- **Network:** no direct route out. An HTTP(S) proxy admits only `registry.npmjs.org`,
  `pypi.org`, `files.pythonhosted.org`, `codeload.github.com`,
  `objects.githubusercontent.com`, `raw.githubusercontent.com`, and `localhost:11434`.
  `strictAllowlist` refuses every other host with no prompt.
- **Git push is not possible** from a sandboxed command: `github.com` and `api.github.com` are
  not allowed (a domain filter can't tell fetch from push, so GitHub read is limited to the
  archive/raw hosts above), and git over SSH can't authenticate through the macOS sandbox proxy.
- **Secrets in the environment** (`GITHUB_TOKEN`, `GH_TOKEN`, `NPM_TOKEN`,
  `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) are unset for sandboxed commands.

Without `--settings`, the project file alone still turns the sandbox on with the same read
denials, write scope, and allowlist, but Claude Code ignores `strictAllowlist` in project
settings, so a host outside the list prompts (in auto mode, the classifier may approve a host
Claude names on the command) instead of being refused. The repo's own files could also loosen
the sandbox. Use the lock.

## Known limits

- **A command denylist is a speed bump, not a boundary.** An agent that can write a file and
  then run it with an allowed program (`python3 x.py`, `npm test`, `make`) can run anything,
  and the hook cannot see what that program does. Only the OS sandbox contains that, and only
  for Bash.
- **The sandbox covers Bash only.** Read, Edit, Write, WebFetch, WebSearch, MCP servers, and
  the hooks themselves run outside it, with Owen's full access. The file tools are held by the
  permission rules and the hook alone; WebFetch and MCP are not covered by D1.
- Commands Owen types at the `!` prompt run unsandboxed.
- The network filter trusts the hostname a client sends and does not inspect TLS, so an allowed
  host is a possible exfiltration path (for example, domain fronting).
- `localhost:11434` (Ollama) goes through the proxy. Clients that bypass the proxy for
  localhost (Claude Code sets `NO_PROXY` for it) are blocked on macOS, because the profile does
  not set `allowLocalBinding`: that would open every localhost port.
- The sandbox reads `student_data_roots.txt` only when `render_settings.py` runs. After editing
  the roots, re-render, re-copy, and re-install.
- **Hook limits.** The inline-code list is not exhaustive: an interpreter the hook doesn't
  know, or a tool with its own scripting (`make`, `git` hooks in a repo it creates, `vim -c`,
  `sqlite3 .shell`), still runs code. A variable set outside the command (`$X` from the
  environment) is opaque; the hook only judges its literal prefix. `rm -rf <worktree root>`
  and `rm -rf *` at the worktree root are denied (not strictly inside), which is deliberate.
- **Denying `~/.claude/projects` blocks Claude Code's own transcripts and auto-memory for the
  agent's tools too.** Persisted large tool outputs live there, so the agent can no longer
  Read them back; memory writes are denied as well.

## Files

| File | Role |
|---|---|
| `dev_guard.py` | The hook (stdlib only). Source of truth; never edit the installed copy. |
| `install_dev_guard.py` | Copies the hook and `sandbox-lock.json` to `~/.claude/hooks/cos/`, read-only, and records their SHA-256. Owen runs it, outside an agent session. |
| `render_settings.py` | Generates `settings.proposed.json` and `sandbox-lock.json`; `--check` reports drift. |
| `settings.proposed.json` | The project profile, for Owen to copy to `.claude/settings.json`. |
| `sandbox-lock.json` | The sandbox lock, passed with `claude --settings`. |
| `dev_safety_probe.py` | Integrity, synthetic hook, and tool-boundary probes. |
| `../../tests/test_dev_guard.py` | Unit tests. |
